Ответы технологическому стеку — Сбер Страхование жизни

Ответы по архитектуре и функционалу платформы для коллег Сбер Страхование жизни.

BankFuture PFP · Конфиденциально · Сбер Страхование жизни · 16 мая 2026 г.

Платформа BankFuture PFP — финансовое планирование для агентов и клиентов. В партнёрском контуре с Сбер Страхование жизни продукт «Подушка безопасности» показывается в расчётах и отчётах; оформление — по реферальной ссылке на стороне Сбера. Развёртывание PFP в инфраструктуре Сбера не предполагается.

«На каком языке программирования реализована система? Используется ли единый стек или микросервисная архитектура? Какова архитектура приложения: монолит, микросервисы? Как организовано взаимодействие между компонентами?»

Ответ. Backend — JavaScript (Node.js 20 LTS), фреймворк Express, доступ к данным — Knex. Единый стек, архитектура — модульный монолит (одно приложение, логика разделена по сервисам в коде; не микросервисы). Личные кабинеты (SPA) общаются с backend по HTTPS REST (/api/...). Внутри backend — синхронные вызовы сервисов и HTTP к внешним API; фоновые задачи — node-cron, генерация PDF — Puppeteer.

«Какие базы данных используются для хранения пользовательских данных, истории действий, инвестиционных предложений и метаданных?»

Ответ. Основное хранилище — MySQL (mysql2): пользователи, клиенты, цели, портфели, продукты, настройки программ (tenant), CRM. История действий — записи в БД по клиенту/целям/отчётам и журналы приложения (Winston). Файлы (PDF, обложки) — S3-совместимое объектное хранилище. История ИИ-чатов (если модуль включён) — отдельные таблицы в той же MySQL.

«Как реализована интеграция с внешними и внутренними сервисами (например, CRM, внешние API)? Используются ли очереди сообщений, брокеры событий?»

Ответ. Интеграции — REST-адаптеры на стороне PFP (в т.ч. CRM, внешние портфельные и продуктовые API — по подключённым партнёрам). Сбер Страхование жизни: расчёт и показ продукта в PFP, переход клиента на оформление по ссылке на ресурс Сбера; API обмена с учётными системами Сбера в текущем контуре нет. Очереди сообщений и брокеры событий (RabbitMQ, Kafka и т.п.) не используются — асинхронность через cron и фоновые задачи в процессе приложения.

«Какие меры реализованы для обеспечения безопасности персональных и финансовых данных пользователей (шифрование, аудит, разграничение прав доступа)?»

Ответ. Аутентификация — JWT, пароли — bcrypt; API — helmet, cors, валидация входных данных. Разграничение доступа — по ролям и изоляции по проекту (tenant). Передача данных — TLS. Секреты — в переменных окружения / secret manager, не в коде. Аудит — централизованное журналирование без секретов и избыточных ПДн в логах. Шифрование на уровне дисков/СУБД — средствами инфраструктуры хостинга.

«Как реализована версионирование API и миграций данных при изменениях в бизнес-логике или структуре БД?»

Ответ. API — спецификация OpenAPI, эволюция с сохранением обратной совместимости, где возможно. БД — версионируемые миграции Knex, применяются при деплое (knex migrate:latest). Изменения бизнес-логики расчётов — через релиз backend и при необходимости миграции данных.

«Есть ли ограничения по используемым библиотекам, фреймворкам или сторонним компонентам (например, корпоративные стандарты, лицензии)?»

Ответ. Зависимости — экосистема npm, преимущественно лицензии MIT/ISC. Ключевые компоненты: Express, Knex, mysql2, axios, jsonwebtoken, bcryptjs, puppeteer (PDF), AWS SDK (S3). Отдельного корпоративного whitelist со стороны PFP для партнёра не предъявляется; при размещении в контуре заказчика ограничения согласуются отдельно.

«Как обеспечивается соответствие требованиям регуляторов (например, хранение данных на территории РФ, аудит действий пользователей)?»

Ответ. Размещение платформы и БД — на территории РФ (инфраструктура оператора PFP). Аудит действий — журналы приложения по регламенту оператора. Данные клиента в сценарии со Сбером обрабатываются в контуре PFP для консультации; передача в Сбер — при действии пользователя (переход по ссылке и оформление на стороне Сбера), если не согласован иной обмен.

«Какие именно AI/ML модели используются внутри продукта?»

Ответ. Используются LLM (большие языковые модели), не классический ML и не дообучение на данных клиентов. Базовая модель — Gemma (google/gemma-3-27b-it). DEV: inference через OpenRouter. PROD: inference на арендованном GPU (immers.cloud), OpenAI-compatible API. Расчёт страховой цели «Подушка безопасности» — не LLM, а детерминированный калькулятор (тариф 1,44% годовых).

«AI функционал построен исключительно на внешних API или у вас есть собственный inference/backend слой?»

Ответ. Есть собственный backend-слой (промпты, маршрутизация диалога, история, streaming, fallback): aiService, aiB2cService, constructorAiService. Вычисление модели (inference) — на prod на GPU в аренде (immers.cloud), на dev — через OpenRouter; единый контракт chat/completions. Собственного ЦОД с GPU нет.

«Какие пользовательские действия или результаты на платформе формируются именно ИИ в реальном времени, а какие обычной back-end логикой?»

Ответ.

  • Backend (без ИИ): все финансовые расчёты и цели (включая страхование жизни), риск-профиль (скоринг анкеты), портфели, PDF/HTML-отчёты, отправка письма со ссылкой на оффер Сбера, CRM.
  • ИИ: чат-ассистент B2C, диалоги конструктора, опциональные текстовые блоки в отчётах (если включены).
«Система принимает адаптивные решения на основе ИИ модели, или все сценарии детерминированы заранее прописанными условиями?»

Ответ. Суммы, тарифы, продуктовые рекомендации и расчёты — детерминированы правилами и формулами. ИИ используется для текста и диалога, не для принятия финансовых решений и не для изменения тарифа или условий договора.

«Улучшается ли качество ИИ-выдачи по мере накопления пользовательских данных и поведения пользователей?»

Ответ. Сейчас — нет автоматического дообучения (fine-tuning) модели на поведении пользователей. Качество ответов повышается за счёт двухэтапной оркестрации контекста: на первом шаге отдельный LLM-вызов (контекст-архитектор) отбирает и сжимает релевантные фрагменты знаний и данных клиента; на втором — основной LLM генерирует ответ уже по подготовленному контексту (в чате B2C и в конструкторе — схема «маршрутизатор → генератор»). В планах развития — использование накопленной истории и поведения для персонализации при том же принципе: финансовые расчёты остаются детерминированными, адаптация касается диалогового слоя.

«Сохраняются ли действия пользователя, оценки, клики, история запросов для последующей оптимизации ИИ-результатов?»

Ответ. История чатов сохраняется для продолжения диалога, не для дообучения модели. Отдельной системы «клики/оценки → улучшение модели» нет.

«Есть ли у ИИ память/контекст между сессиями, или каждый запрос обрабатывается как независимый одноразовый промпт?»

Ответ. В чат-сценариях — контекст и история из БД между обращениями. В разовых задачах (например, абзац в отчёте) — как правило один запрос с переданным контекстом, без долгой памяти между отчётами.

«Может ли система объяснить на основании каких факторов ИИ принял ту или иную реккомендацию?»

Ответ. Расчёты объяснимы правилами методики (формулы, анкета). Тексты LLM — без гарантированного формального explainability; для значимых цифр в отчёте опора на детерминированный расчёт, не на вывод модели.

«Реализована ли многошаговая ИИ-оркестрация или это одиночный запрос-response к LLM API?»

Ответ. Оба варианта: простые задачи — один запрос к API; чат B2C и конструктор — многошаговая схема (стадия диалога → ответ). Отправка оффера Сбера клиенту — обычный backend, без LLM.

«Если полностью убрать ИИ компоненты, какой процент функциональности продукта сохранится?»

Ответ. Ориентировочно 85–95%: расчёты, отчёты, страховая цель с продуктом Сбера, реферальное письмо, CRM и остальное ядро PFP. ИИ — опциональный модуль.

«Какие пользовательские функции вообще не смогут работать без ИИ слоя, если есть?»

Ответ. Без ИИ не работают: B2C чат-ассистент, LLM-диалог конструктора, опциональные AI-тексты в отчётах, AI-пояснения риск-профиля (скоринг анкеты при этом работает), боты при привязке к LLM. Работают без ИИ: весь сценарий с продуктом «Подушка безопасности» (расчёт, отчёт, ссылка, email агенту → клиенту).
