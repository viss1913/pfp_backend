# Резолют ↔ ПФП: методы, типы продуктов, статусы (MVP)

**Цель:** зафиксировать на 1 странице, что именно нужно ПФП от интеграции с Резолют (методы API), как мы передаём **тип продукта**, какие **статусы** нам важны, и какие данные по клиенту/позициям передаём.

Документ дополняет (не заменяет) детализацию полей и примеры payload в:  
`docs/partners/RESOLUT_API_REQUIREMENTS_PFP.md`.

## 1) Тип продукта (product_type / product_kind)

ПФП на своей стороне уже оперирует таксономией продуктов (условно: `Bonds`, `NSZH`, `ISZH` и т.д.).  
Для интеграции с Резолют нам нужен **единый признак типа**, чтобы:

- маршрутизировать параметры (разные минимальные наборы полей)
- определять, какой обработчик/форма в Резолют применяется
- корректно валидировать портфель на стороне Резолют

### Предлагаемая таксономия (на согласование)

| Тип в ПФП (пример) | Код типа для интеграции (предлагаем) | Смысл / примечание |
|---|---|---|
| `Bonds` | `BONDS` | Рыночные облигации / облигационные продукты |
| `NSZH` | `NSZH` | Накопительное страхование жизни |
| `ISZH` | `ISZH` | Инвестиционное страхование жизни |
| `Deposits` | `DEPOSIT` | Банковские вклады/депозиты |
| `Funds` | `FUND` | ПИФ/ETF/фонды (если будут на следующих этапах) |
| `Stocks` | `STOCK` | Акции (если будут на следующих этапах) |
| `Other` | `OTHER` | Прочее/нестандартные продукты |

**Важно:** если в Резолют типы называются иначе — ок, но нужна **таблица соответствия** и фиксированный словарь значений для API.

## 2) Маппинг продукта: 1:1 и 1:many

В ПФП “продукт предложения” может быть **укрупнённым** (например, “Защита жизни”), а в Резолют оформление идёт по **конкретной программе/тарифу** (их может быть несколько).

Поэтому маппинг допускает **1:many**:

- `pfp_offer_code` → список `resolut_program_code` (или `resolut_product_code`)
- у каждой привязки может быть `is_active` и правила применимости (возраст, срок, минимальный взнос, канал и т.п.)

**Рекомендация по ключам:**

- основной ключ привязки: **`resolut_program_code`** (стабильный код)
- `resolut_program_id` (внутренний ID) — *опционально*, как технический атрибут (может быть средо-зависим и нестабилен)

## 3) Методы интеграции: что нужно ПФП

### MVP (этап 1)

1. **Получить каталог/маппинг актуальных продуктов**
   - `GET /products` (или аналог)
   - ПФП использует это, чтобы **не рекомендовать** и **не отправлять** в оформление неактуальные продукты/программы

2. **Передать портфель в оформление (основной метод)**
   - `POST /portfolios` (или аналог)
   - Результат на стороне Резолют: создаются **персона клиента** + **набор заявлений/договоров** + связь по `portfolio_id`
   - Ответ: `portfolio_id`, список `application_id` по позициям, и данные для **handoff** (deep link / token)

### Опционально (если нужно бизнесу)

3. **Котировка до оформления**
   - `POST /quotes` (или аналог)
   - Нужна только если требуется “официальная котировка Резолют” *до* создания заявлений/черновиков
   - “Пересчитать” = тот же метод котировки (идемпотентно) или котировка по `application_id` (если у вас так принято)

### Полезно на следующих этапах

4. **Получить статус портфеля/заявлений**
   - `GET /portfolios/{portfolio_id}` или `GET /applications?portfolio_id=...`
   - Это нужно, если ПФП должен показывать “что в итоге произошло” после перехода в Резолют

## 4) Статусы: минимально достаточные для ПФП

ПФП не обязан знать всю внутреннюю статусную модель Резолют. Нам достаточно **верхнеуровневых** статусов.

### Предлагаемый минимальный набор

| Статус | Смысл |
|---|---|
| `DRAFT` | Создано, оформление не завершено (“думает/в процессе”) |
| `IN_PROGRESS` | Активно заполняют/редактируют |
| `SUBMITTED` | Отправлено на обработку/регистрацию (если применимо) |
| `SIGNED` | Подписано (если стадия существует отдельно) |
| `COMPLETED` | Договор/пакет успешно завершён |
| `CANCELLED` | Отменено/брошено |
| `FAILED` | Ошибка/отказ (с кодом причины) |

**Продление** (`RENEWAL`) — имеет смысл добавлять как отдельный сценарий только когда появится соответствующая бизнес-логика (этап 2+).

## 5) Какие данные передаём (общая логика)

### Данные клиента (person)

Да: ПФП передаёт в Резолют данные клиента в объёме, достаточном для создания персоны и черновиков заявлений.

Рекомендуем разделить на:

- **минимум для черновика**: ФИО, ДР, пол (если влияет), телефон/email (если есть)
- **полные данные для договора**: паспорт/адреса/и т.п. — обычно дозаполняются уже в Резолют при оформлении

### Данные портфеля и позиций

- `external_portfolio_id` (наш устойчивый ID) — для идемпотентности и склейки
- `product_type` + `resolut_program_code` (или `resolut_product_code`) по каждой позиции
- `parameters` по позиции — минимально достаточный набор **диктует Резолют** для котировки/создания заявления
- `sales` блок — агент/канал/партнёрские коды (чтобы у вас сразу собирался SALES)

### Про “текущий капитал” и прочие фин. метрики

Передавать в Резолют стоит **только то**, что:

- требуется для котировки/валидации конкретного продукта, **или**
- нужно для формирования заявления/договора (обязательное поле)

Иначе это остаётся внутри ПФП (рекомендательная логика), чтобы не раздувать контракт и не плодить вопросы по источнику правды.

---

## 6) Минимальный результат в ответе Резолют на `POST /portfolios`

- `portfolio_id` (ваш)
- `person_id` (ваш)
- `applications[]`: `{ application_id, resolut_program_code, status }`
- `handoff`: `{ url }` или `{ base_url, access_token, expires_at }`
