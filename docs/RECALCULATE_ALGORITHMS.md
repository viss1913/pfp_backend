# Алгоритмы пересчёта целей (recalculate)

Документ описывает, **как** пересчитываются цели при вызове `POST /api/client/:id/recalculate` в зависимости от типа цели и от того, какие параметры пользователь изменил. Параметры по типам целей перечислены в [GOAL_EDIT_LOGIC.md](notes/GOAL_EDIT_LOGIC.md); здесь — формулы и ожидаемое поведение.

---

## Общая схема recalculate

1. **Вход**: существующий клиент из БД + тело запроса (опционально `client`, опционально одна цель `{ goal_id, ... }` или массив `goals[]`).
2. **Подготовка цели**: для каждой изменённой цели вызывается `GoalRecalculator.prepare(existing, patch)` — слияние существующей цели с патчем; числовые поля приводятся к Number.
3. **Расчёт**: `CalculationService.calculateFirstRun(client, goals, targetGoalId, previousCalculation, { isFirstRun: false })`. Smart Allocation при recalculate не запускается (капитал по целям «заморожен» из предыдущего расчёта).
4. **Сохранение**: при одиночном обновлении цели в БД пишется `updatedGoalData` из подготовленного goalsMap (т.е. **входные** данные цели), а не поля из результата расчёта. Исключение: `goals_summary` сохраняется как JSON результата расчёта.

**Важно**: если для типа цели при изменении одного параметра должен пересчитываться другой (например, при смене ежемесячного пополнения — «желаемый доход в месяц»), это должно либо возвращаться в `summary` и подставляться в цель при сохранении, либо считаться в калькуляторе и записываться в цель на бэкенде. Иначе фронт/БД останутся со старым значением.

## По типам целей

### 1. Госпенсия (PENSION, goal_type_id = 1)

| Что меняется | Что пересчитывается |
|--------------|----------------------|
| `target_amount` / желаемая пенсия в месяц | Размер выплат, капитал в ОПС, рекомендации по ИПК и т.д. |
| `initial_capital`, `ops_capital`, `ipk_current`, `inflation_rate`, `term_months` (срок до выхода на пенсию) | Прогноз пенсии, дефицит/профицит, рекомендации. |

- **Формула**: желаемая пенсия в будущих ценах = `target_amount * (1 + inflation_rate/100)^years_to_pension`. Дальше используются гос. калькуляторы (ИПК, баллы, ОПС).
- **Пересчёт обратно**: при изменении только капитала/ИПК пересчитывается достижимая пенсия; значение, отображаемое как «желаемая пенсия в месяц», может браться из расчёта (если продукт это поддерживает).

**Основной выходной параметр:** рекомендуемое **ежемесячное пополнение** под заданную желаемую пенсию (через пенсионный калькулятор + портфель).

---

### 2. Пассивный доход (PASSIVE_INCOME, goal_type_id = 2)

**Входы**: `target_amount` или `desired_monthly_income` (желаемый доход в месяц в **сегодняшних** деньгах), `term_months`, `initial_capital`, `inflation_rate`, `monthly_replenishment` (опционально).

**Логика калькулятора** (`PassiveIncomeCalculator`):

1. Желаемый доход в месяц (вход): `initialDesiredIncome = goal.desired_monthly_income || goal.target_amount`.
2. Желаемый доход в ценах будущего: `desiredIncomeFuture = initialDesiredIncome * (1 + inflation_rate/100)^(term_months/12)`.
3. Требуемый капитал к концу накопления (фаза выплат):  
   `requiredCapitalFuture = (desiredIncomeFuture * 12 * 100) / payoutYieldPercent`  
   (доходность выплат из настроек `passive_income_yield`).
4. Если задано **`monthly_replenishment`**: симуляция накопления с этим пополнением → получаем `simResult.totalCapital` (фактический капитал к концу).
5. Если **не** задано: подбор `monthly_replenishment` по целевым `requiredCapitalFuture` (обратный расчёт пополнения).

**Что возвращается в `summary`** (ключевые выходы):

- `target_amount_initial` — сейчас всегда равен **входному** `initialDesiredIncome` (желаемый доход в месяц в сегодняшних деньгах).
- `monthly_replenishment` — подобранное или переданное пополнение.
- `projected_capital_at_end` — капитал к концу при заданном/подобранном пополнении.
- `required_capital_at_end` = `requiredCapitalFuture`.

**Основной выходной параметр:** рекомендуемое **ежемесячное пополнение** (`monthly_replenishment`) под заданный желаемый доход.

#### Ожидаемое поведение при изменении только ежемесячного пополнения

При изменении пользователем **только** `monthly_replenishment` логично считать, что «стоимость цели» в UI — это **достижимый доход в месяц в сегодняшних деньгах** при таком пополнении, а не старый введённый желаемый доход.

- **Ожидание**: пересчитывается и обновляется «желаемый доход в месяц в сегодняшних деньгах» = какой месячный доход в текущих ценах обеспечит накопленный капитал `projected_capital_at_end` при доходности выплат `payoutYieldPercent`:
  - доход в месяц в будущих ценах: `(projected_capital_at_end * payoutYieldPercent / 100) / 12`;
  - в сегодняшних: делим на `(1 + inflation_rate/100)^(term_months/12)`.
- **Текущее поведение (баг)**: при смене `monthly_replenishment` значение `target_amount_initial` в ответе и в цели **не пересчитывается** — остаётся старый `initialDesiredIncome`. В БД при сохранении цели после recalculate пишутся только входные данные из запроса (existing + patch), т.е. новый `monthly_replenishment`, но **не** новый «достижимый доход» как `target_amount` / `desired_monthly_income`.

**Итог**: при изменении ежемесячного пополнения в цели «Пассивный доход» новая «стоимость цели» (желаемый доход в месяц в сегодняшних деньгах) не пересчитывается и не сохраняется. Нужна доработка: в калькуляторе при заданном `monthly_replenishment` считать достижимый доход и возвращать его как `target_amount_initial` (и при необходимости обновлять сохраняемую цель полями `target_amount` / `desired_monthly_income` из результата расчёта).

### 3. Крупная покупка (OTHER, goal_type_id = 4, 6, 9)

| Что меняется | Что пересчитывается |
|--------------|----------------------|
| `target_amount` (стоимость покупки сегодня) | Целевая сумма в будущем с учётом инфляции, нужное пополнение/дефицит. |
| `term_months`, `initial_capital`, `inflation_rate` | То же. |

- **Формула**: целевая сумма в будущем = `target_amount * (1 + inflation_monthly)^term_months`. Дальше — симуляция накопления и сравнение с этой суммой.

**Основной выходной параметр:** рекомендуемое **ежемесячное пополнение** под стоимость покупки.

---

### 4. Инвестиции (INVESTMENT, goal_type_id = 3)

Пересчитываются срок, стартовый капитал, ежемесячное пополнение и прогноз капитала к концу. «Стоимость цели» как отдельная величина для этого типа не задаётся в том же смысле, что для пенсии или пассивного дохода.

**Основной выходной параметр:** **итоговый капитал** к концу срока.

---

### 5. Защита жизни (LIFE, goal_type_id = 5)

Пересчёт страховой суммы (`target_amount`) и срока (`term_months`), интеграция с НСЖ/внешними API по контракту.

**Основные выходные параметры:**
- рекомендуемое **ежемесячное пополнение** (взнос по программе);
- требуемый **первоначальный капитал** (если продукт допускает единовременный взнос).

---

### 6. Финрезерв (FIN_RESERVE, goal_type_id = 7)

Цель в виде целевой суммы к концу срока; пересчитываются `initial_capital`, `monthly_replenishment`, `term_months` и достижимая сумма.

**Основной выходной параметр:** **итоговый капитал** (достижимая сумма резерва к концу срока).

---

### 7. Ежемесячный процент / рента (RENT, goal_type_id = 8)

Пересчёт дохода от заданного `initial_capital` по ставке ренты (риск-профиль и настройки).

**Основной выходной параметр:** **ежемесячный доход** от капитала.

---

## Где смотреть в коде

- Подготовка целей при recalculate: `src/controllers/clientController.js` → `recalculate()` → `goalRecalculator.prepare(existing, patch)`; рекалькуляторы по типам: `src/algorithms/recalculators/` (в т.ч. `PassiveIncomeRecalculator.js`).
- Расчёт по типам: `src/services/calculationService.js` → `calculateFirstRun()`; калькуляторы: `src/algorithms/calculators/` (в т.ч. `PassiveIncomeCalculator.js`).
- Сохранение цели после recalculate: `clientController.recalculate` → `clientService.updateGoal(clientId, goalId, updatedGoalData)` — в БД уходит только подготовленная цель из goalsMap, без подстановки полей из `summary` расчёта.

---

## Кратко по багу «пассивный доход + смена пополнения»

- **Ожидание**: после смены ежемесячного пополнения обновляется «стоимость цели» = достижимый доход в месяц в сегодняшних деньгах.
- **Сейчас**: не обновляется; в ответе и в БД остаётся старый `target_amount` / `desired_monthly_income`.
- **Что сделать**: в `PassiveIncomeCalculator`, когда задан `monthly_replenishment`, после симуляции вычислить достижимый месячный доход в сегодняшних ценах и вернуть его в `summary.target_amount_initial`; при сохранении цели после recalculate для типа PASSIVE_INCOME подставлять в цель `target_amount` и/или `desired_monthly_income` из результата расчёта (если пересчёт «по пополнению» был выполнен).
