## Назначение

Агент помогает быстро и безопасно править PDF-отчет Ростех, в первую очередь пенсионные страницы и связанный рендер.

## Что считать источником правды

- Дизайн: Figma-макет Ростех (конкретный node-id страницы).
- Данные для страниц: ответы API (`/api/client/:id`, `/api/pfp/reports/:id`) и `goals_summary` клиента.
- Для налоговых льгот:
  - сначала пробуем `goal.summary`,
  - если там нули/пусто — fallback на `overall_plan.tax_benefits.totals`.

## Где работает

- `src/reports/themes/rostech/buildRostechPensionPagesHtml.js`
- `src/services/reportPdfService.js`
- `src/reports/themes/reportRenderers.js`

## Структура страниц для цели «Достойная пенсия»

Актуальный порядок страниц, который ведем и обновляем по мере реализации:

1. Заглавная страница.
2. Описание цели.
3. Госпенсия.
4. Дополнительная пенсия.
5. Портфель + резюме.
6. Налоговое планирование.
7. Методика расчета госпенсии (пока не реализована в финальном виде, держим как TODO).

Правило обновления:
- При добавлении/переносе/удалении страниц сразу обновлять этот список.
- Для каждого пункта по возможности фиксировать `node-id` из Figma и место в рендере.

## Как переносить дизайн шаблонов

1. Берем конкретный `node-id` из Figma для страницы.
2. Если нужно снять верстку из макета или уточнить детали слоя/типографики, подключаем `figma-design-workflow`.
3. Для каждой страницы фиксируем соответствие:
   - Figma `node-id`,
   - HTML-шаблон (`src/reports/goalPages/preview-*.html` и/или рендер в `buildRostechPensionPagesHtml.js`),
   - ожидаемые данные из API.
4. Правим только нужный блок/страницу (не делаем «массовый рефакторинг» всего файла).
5. Сохраняем существующие данные и формулы, меняем в основном верстку:
   - типографика,
   - интервалы между блоками,
   - структура карточек,
   - цвета/плашки/графики.
6. Если в макете есть фиксированные текстовые фразы с переменными:
   - переменные должны быть из расчета,
   - формат денег и лет согласован с текущим стилем отчета.

## Обязательный рабочий цикл

1. Зафиксировать источник данных для блока: `goal.summary` и fallback из `overall_plan.tax_benefits.totals`.
2. Внести правку в верстку/текст/формулу без изменения чужих тем.
3. Проверить lint измененных файлов.
4. Прогнать генерацию:
   - `POST /api/client/first-run` (через логин агента/JWT),
   - затем `scripts/test_report_client.js <client_id>`.
5. Сверить, что в PDF попали реальные значения (не нули), особенно:
   - `cofinancing_2026`,
   - `deduction_2026`,
   - годы в строках льгот.

## Практический чек тестирования (минимум)

1. Логин агентом в API.
2. Создать тест-клиента через `first-run` с понятными параметрами (доход, капитал, цель).
3. Проверить JSON клиента:
   - `goals_summary.summary.tax_benefits_summary.totals`,
   - `goals_summary.goals[0].summary`,
   - `details.monthly_schedule` (где реально срабатывают deduction/cofinancing).
4. Сгенерить PDF:
   - `node scripts/test_report_client.js <client_id>`.
5. Проверить в PDF:
   - суммы и годы в текстах,
   - отсутствие лишних блоков,
   - соответствие отступов/размеров макету.

## Частые ошибки и как не наступить

- Ошибка: брать путь `overall_plan.summary.tax_benefits_summary.totals`, когда в реальном отчете данные лежат в `overall_plan.tax_benefits.totals`.
- Ошибка: использовать `??` при fallback и получать `0 ₽` (ноль не null/undefined).
- Ошибка: округлять налоговый вычет до целых — для вычета оставлять 2 знака.
- Ошибка: ломать соседние страницы при правке одной (держать изменения локальными).

## Критичные проверки перед завершением

- На странице прогноза пенсии нет лишнего верхнего хедера.
- На странице плана (`59:132`) сохранена структура «длинный текст + график 3 столбца + плашка доходности».
- Для вычета формат с 2 знаками после запятой.
- Если `goal.summary.*` = 0, корректно срабатывает fallback из totals.
- PDF после правок реально пересобран и путь к файлу зафиксирован.

## Запреты

- Не хардкодить годы и суммы.
- Не удалять важные строки про софинансирование и налоговый вычет.
- Не править нерелевантные модули без запроса.
