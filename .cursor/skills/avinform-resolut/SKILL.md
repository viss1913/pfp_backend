# AV Inform / Resolut Integration Skill

Этот skill используется для задач интеграции **AV Inform/Resolut** в backend PFP.

## Когда использовать

Используй skill сразу, если задача включает хотя бы одно из:
- авторизация в AV/Resolut (`authorize` внутри `POST /auth/login`, Bearer в `resolutSessionStore`, опционально `RESOLUT_STATIC_KEY` для фона);
- сессия Резолюта после логина агента (`resolutSessionStore`, `exchangePasswordForSessionKey`);
- синхронизация каталога продуктов (`products`);
- получение котировок (`quote`);
- расчёт НСЖ LIFE через Резолют (`resolutNsjQuoteService`, `assetShort`);
- доходность инструмента в портфеле из котировки (`resolutPortfolioQuoteYieldService`, поля `products.resolut_pfp_code` / `resolut_quote_p_type`, только `RESOLUT_PROJECT_ID`);
- PDF: те же Finam-шаблоны для `projectId` из `FINAM_REPORT_PROJECT_IDS` (в т.ч. 23);
- подготовка этапа 2: `portfolio`, `client`, `link`;
- сверка маппинга `projectId` и продуктовых кодов между PFP и AV/Resolut.

Актуальная выжимка для агента Cursor: `.cursor/agents/avinform-resolut.md`.

## Жесткие границы (обязательно)

Перед началом любой работы:
1. Проверь, что задача относится к AV Inform/Resolut.
2. Отдельно проверь, не затрагивает ли она Finam/Comon, Rostech или другие несвязанные контуры (исключение: общие HTML-шаблоны отчёта Finam для проекта AV по списку `FINAM_REPORT_PROJECT_IDS` — согласовано продуктом).
3. Если затрагивает или есть неоднозначность — остановись и запроси явное подтверждение пользователя.

Нельзя менять чужие контуры по умолчанию (кроме явно оговорённого reuse шаблонов PDF).

## Рабочий процесс

### Шаг 1. Зафиксировать входные данные
- Базовый URL стенда.
- Для ручных тестов: пары логин/пароль (те же, что в ЛК PFP и у AV); для фона — наличие `RESOLUT_STATIC_KEY` при необходимости.
- Целевой `projectId` в PFP для AV-контура.
- Текущий статус интеграции: что уже реализовано, что нужно добавить.

### Шаг 2. Проверка границ задачи
- Укажи, какие файлы/модули допустимо менять в текущем scope.
- Укажи, какие зоны явно запрещены к изменениям.

### Шаг 3. Проверка auth-контура (этап 1)
- Проверить обмен на Bearer при `POST /auth/login` (агент, `project_id === RESOLUT_PROJECT_ID`):
  - успех на валидных реквизитах;
  - 401 при неверной паре у Resolut;
  - поведение при таймауте/недоступности.
- Секреты: пароль агента не хранится для Resolut в env; опционально только `RESOLUT_STATIC_KEY` / `resolut_static_key` для фоновых вызовов.

### Шаг 4. Проверка products/quote (этап 1)
- Зафиксировать контракт ответов `products` и `quote`.
- Проверить достаточность полей для PFP-расчета и последующей передачи в оформление.
- Выделить недостающие поля и несоответствия.

### Шаг 5. Подготовка этапа 2 (без ломки текущего контура)
- Определить минимальный контракт для `portfolio/client/link`.
- Зафиксировать структуру маппинга внутренних ID и кодов AV.
- Сформировать список preconditions для безопасного внедрения.

### Шаг 6. Итоговая проверка изоляции
- Подтвердить, что изменения ограничены AV-контуром.
- Явно указать, что Finam/Rostech/прочие контуры не затронуты.

## Формат результата

В ответе обязательно:
1. Что проверено.
2. Что работает.
3. Что не работает.
4. Какие данные нужны от партнера.
5. Что делать следующим шагом в PFP.
6. Подтверждение по границам: какие контуры не затронуты.
