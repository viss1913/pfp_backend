# Запрос обратной связи: Интеграция API и DX (Developer Experience)

Коллеги из Фронтенд-команды!

Для нас важно, чтобы API был не только функциональным, но и удобным в разработке. Ваше мнение критически важно для следующего цикла доработок. Пожалуйста, изучите текущую реализацию (см. `MESSAGE_FOR_FRONTEND_DEV.md`) и дайте фидбек по следующим пунктам:

### 1. Структура данных и графики
- Удобен ли объект `consolidated_portfolio` для ваших библиотек графиков (Recharts, Chart.js и т.д.)?
- Предпочли бы вы более «плоские» (flat) данные или текущая вложенная структура допустима?
- Достаточно ли деталей в `cash_flow_allocation` для Bar Charts, или вам нужны заранее рассчитанные итоги (месяц/год) для всего?

### 2. Процесс пересчета (`/recalculate`)
- Понятна ли логика «частичного обновления»? (когда отправляются только измененные поля).
- Как вам удобнее обновлять цели: целиком массивом или нужны отдельные эндпоинты для каждой цели (`PUT /goals/:id`)?
- Достаточна ли скорость ответа бэкенда для реализации сценариев «Что если?» в реальном времени?

### 3. Ошибки и валидация
- Достаточно ли описательны сообщения об ошибках (400 Bad Request) для показа пользователю в UI?
- Нужны ли вам специфические коды ошибок (например, `INSUFFICIENT_POOL_CAPITAL`, `INVALID_TERM`)?

### 4. Логика редактирования целей
- Хватает ли документа `GOAL_EDIT_LOGIC.md` для построения форм?
- Есть ли параметры, которые, по вашему мнению, должны быть редактируемыми, но сейчас скрыты в API?

### 5. Удобство разработки (DX)
- Нужен ли вам Swagger UI для интерактивного тестирования эндпоинтов?
- Кажутся ли названия полей (snake_case) логичными и последовательными?
