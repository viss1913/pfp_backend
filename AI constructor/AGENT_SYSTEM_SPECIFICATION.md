# Техническое задание: Агентская платформа управления ИИ‑ботами

## 1. Общее описание проекта
Цель проекта — создать масштабируемую систему, где **Администратор** настраивает глобальные сценарии общения (CJM), а **Агенты** подключают собственных Telegram-ботов, которые работают по этим сценариям, но сохраняют уникальный стиль общения агента.

Система наследует архитектуру проекта **BankFuture**, используя двухшаговую модель AI:
1. **Классификатор**: Определение текущей стадии диалога (команды).
2. **Ответчик**: Формирование ответа на основе инструкций конкретной стадии и профиля агента.

---

## 2. Сущности и структура данных (БД)

### 2.1. Агенты (Agents)
Те, кто подключает своих ботов.
- `id`: Unique ID
- `user_id`: ID пользователя в системе (админ/агент)
- `name`: Имя агента
- `created_at`: Дата регистрации

### 2.2. Боты (Bots)
- `id`: Unique ID
- `agent_id`: FK на таблицу агентов
- `name`: Публичное имя бота
- `token`: Telegram API Token
- `communication_style`: Текст, описывающий манеру общения (например: "Общайся дерзко, используй молодежный сленг" или "Будь официально-деловым").
- `base_brain_context`: (Скрыто) Базовая роль системы, общая для всех.
- `is_active`: Статус (вкл/выкл)

### 2.3. Команды CJM (AI Commands)
Сценарии, по которым бот ведет клиента.
- `command`: Ключ (например, `/start`, `/meeting`, `/pricing`)
- `classifier`: Инструкции для AI, как понять, что нужно переключиться на эту команду.
- `response`: Инструкции для AI, как отвечать на этой стадии.
- `section`: Группировка (например, "Продажи", "Поддержка").
- `is_template`: Флаг (true — глобальный шаблон, false — кастомная команда бота).
- `bot_id`: (Nullable) Если команда привязана к конкретному боту.

### 2.4. Пользователи/Клиенты (Users/Clients)
Люди, которые пишут в ботов.
- `user_id`: Telegram ID клиента
- `bot_id`: К какому боту привязан (пользователь может быть один в разных ботах)
- `nickname`: Имя из Telegram
- `user_context`: Персональные заметки о клиенте (фиксируются ИИ или вручную).

## 3. Модули системы

### 3.1. Модуль 1: Настройка Базового ИИ (Admin Panel)
Здесь Администратор настраивает "движок" системы:
- **Глобальный CJM**: Редактор команд (`classifier` и `response`). Эти команды становятся шаблонами для всех ботов агентов.
- **Глобальные секции**: Управление разделами команд.
- Блоки управления пользователями и историей всех переписок.

### 3.2. Модуль 2: Кабинет Агента (Agent Dashboard)
Интерфейс для конечного агента:
- **Подключение бота**: Форма ввода (Имя, Токен, Стилистика).
- **Настройка стиля**: Поле для ввода `communication_style`.
- **Мои Клиенты**: Список пользователей, которые писали именно в его бота.
- **Диалоги**: Просмотр истории переписки (Read Only или с возможностью перехвата).

## 4. Логика динамического контекста (Алгоритм)

Работа бота происходит в 2 этапа при каждом входящем сообщении:

### Шаг 1: Определение стадии (State Management)
1. Система берет текущую стадию пользователя из таблицы `sessions` (например, `/start`).
2. Из БД выгружается `classifier` для этой команды.
3. Отправляется запрос к AI: `[ classifierContext ] + [ userMessage ]`.
4. AI возвращает ТОЛЬКО ключ следующей команды (например, `/meeting`).

### Шаг 2: Генерация ответа (Response Generation)
Система собирает "Слоеный промпт":
1. **Слой 1 (Системный)**: `base_brain_context` (Кто мы такие).
2. **Слой 2 (Агентский)**: `communication_style` (Как мы говорим).
3. **Слой 3 (Сценарный)**: `response` из текущей команды (Что именно сказать на этом этапе).
4. **Слой 4 (Персональный)**: `user_context` (Что мы знаем о клиенте).
5. **Слой 5 (История)**: Последние 10-15 сообщений диалога.

Все это отправляется в AI, и результат уходит пользователю в Telegram.

## 5. API Архитектура

### 5.1. Admin API (`/api/admin/*`)
- `GET /bots`: Список всех ботов всех агентов.
- `POST /templates`: Создание глобальных команд CJM.
- `GET /stats`: Глобальная статистика по сообщениям и пользователям.

### 5.2. Agent API (`/api/agent/*`)
- `POST /register-bot`: Создание/обновление бота (токен, имя, стиль).
- `GET /my-clients`: Список клиентов только этого агента.
- `GET /messages/:userId`: История переписки конкретного клиента.
- `PUT /client-context/:userId`: Обновление заметок о клиенте вручную.

## 6. Рекомендации исполнителю (Tips)
1. **Изоляция данных**: При запросе сообщений или клиентов ОБЯЗАТЕЛЬНО фильтровать по `bot_id` или `agent_id`, чтобы агенты не видели данные друг друга.
2. **Управление токенами**: Использовать библиотеку (например, `node-telegram-bot-api`), которая позволяет динамически создавать экземпляры ботов и останавливать их при невалидности токена.
3. **Отказоустойчивость**: Каждый бот должен работать в `try-catch`, чтобы ошибка в токене одного агента не "вешала" весь сервер.
4. **Логирование**: Сделайте единую таблицу `control_logs`, куда админ может смотреть для отладки классификации (какая команда была определена).
